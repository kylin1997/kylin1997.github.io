你的 AI 编码智能体，需要一个管理者

发表于2026-11-11|更新于2026-11-11|harness03-runmulti-agent

原文标题：Your AI coding agents need a manager
作者：Addy Osmani
发布日期：2026 年 1 月 8 日
原文链接：https://addyosmani.com/blog/coding-agents-manager/

让一个人成为优秀技术负责人或管理者的能力，可以直接迁移到 AI 编码上。一旦你开始并行跑多个智能体，你要做的就不再只是调试上下文，而是管理一个团队：清晰表达、任务分派、验证闭环、异步沟通。随着智能体编排日渐成为主流，工作的形态正在改变。

在不远的将来，我认为杠杆率最高的开发者，会像是以异步为先的管理者，带着一小队并行工作的 AI 编码智能体。如今智能体已经能在后台、在隔离环境中干实实在在的活，并交回可评审的成果——通常是一个拉取请求（PR）。质量检查当然还是必须的，但瓶颈已经不再是「智能体能不能写代码？」，而是「这个东西我们该不该做？」以及「我能不能把多个干这活的智能体管好？」。

我们已经能看到预示这一未来的工作流。Claude Code 的创造者 Boris Cherny 最近发的一条帖子火了，因为它把这种转变讲得非常具体：他在本地终端标签页里跑 5 个 Claude Code 会话，浏览器里再跑 5～10 个，甚至还会用手机启动会话，之后再回来看结果。这就是编排。

与此同时，一些善于思考的工程师也在用更审慎的视角记录「并行智能体」这种工作方式。Simon Willison 的观点是我反复回看的一篇：天然的瓶颈不是生成代码，而是评审代码。不过他依然认为并行派发任务有真实价值，前提是你对自己的注意力带宽足够诚实，并且选的任务不会把脑子压垮。我一直在搭建类似的工作流，也同意这一点：价值是真实的，但前提是把它当成管理，而不是魔法。

这就是心态上的转变：你不再是和单个智能体结对，而是在带一个小团队。

也正因如此，让一个人成为优秀技术负责人、工程经理或工程领导者的那些能力，突然之间就直接等同于「擅长 AI 编码」。因为规模化的 AI 编码不再是一个提示词问题，而是一个管理问题。

新工作流的心智模型

我把它想成并行的两种模式。

第一种是本地、高介入度、始终保持人在回路的会话。用于架构决策、棘手的重构、产品上的细微差别、含糊不清的需求，以及一切由品味和判断力主导的工作。你在和智能体结对，实时纠偏，并做出那些需要智能体并不具备的上下文信息才能下的判断。

第二种是异步运行的云端或后台会话。用于边界清晰、范围聚焦的任务：常规功能、模式明确的迁移、测试生成、文档更新、依赖升级、小型缺陷修复、局部重构。你把任务派发出去，切去做别的事，回来再评审产出。

这种划分和现代工具的演进方向严丝合缝。云端智能体（想想 GitHub Copilot Agent、Claude Web、Codex、Jules 等）被明确定位为可并行、沙箱隔离的任务：能写代码、能跑命令、能提交变更供你评审。

GitHub 的 Copilot 编码智能体也是类似的定位——一个异步后台智能体，先开一个草稿 PR，在后台干活，然后请求评审，你可以在评审里提意见让它继续迭代。而各平台正在走向面向多个智能体（而不只是单个）的「任务控制台」式看板。GitHub 甚至预告了「Agent HQ」，把它作为在一个地方协调多个第三方编码智能体的控制平面，包括让它们并行跑同一批任务以对比产出。

于是问题就从「哪个模型写的代码最好？」，更多变成了「我能不能像带一支高绩效团队那样来运作这件事？」

管理能力正是在这里登场。

为什么管理能力能让你更擅长 AI 编码

关于高效管理技能，我曾专门深入写过。

带人的时候，你会用最痛的方式学到：产出的质量是在上游决定的。含糊不清、归属不明、缺少「完成」的定义、没有反馈闭环，都会带来反复返工。当你的「团队」是一群速度极快、非人类的智能体时，情况同样如此——甚至更甚。

Anthropic 的 Claude Code 最佳实践指南把这话说得很直白：一开始就把要求写具体，能实质性地提高成功率、减少中途纠偏。这明明就是管理者的语言，哪怕它是写给一个工具看的。

以下是迁移度最高的四项能力。

清晰的边界定义：写任务简报，别只给感觉

如果含糊会杀死智能体的有效性，那你的工作就是把「想法形状」的念头，变成一份经得起实现环节考验的任务简报。这恰恰是优秀管理者做的事：把意图转化为可执行的东西。

一份实用的智能体任务简报应覆盖：目标结果（做完后什么应当成立）、背景上下文（这件事落在代码库哪个位置、有哪些既有模式）、约束条件（性能、安全、API 形态、依赖规则、代码风格约定）、非目标（我们明确不做什么）、验收标准（具体可查的条件，比如测试通过、接口按预期行为响应）、集成说明（哪些文件不可触碰、接口接缝应落在哪里），以及验证方案（我们如何确认它真的能用）。

这决定了你拿到的是一个干净的 PR，还是上千行你根本不敢信的烂摊子。

有两个做法能让这件事轻松得多。第一，把智能体指向已有的模式——Anthropic 的指南明确建议点名你希望它参照或更新的文件，这样它会锚定在真实约定上，而不是自创一套。

第二，把长期有效的规则放在智能体总能找到的地方。OpenAI 的 Codex 文档如今已把这一点写成标准做法：用 AGENTS.md 文件给出一致的预期，说明要跑哪些测试、lint 规则、依赖策略和文档要求。如果你带过新人熟悉代码库，这一幕会很熟悉：在他们动手写之前，先给地图、给约定、给「完成」的定义。

分派：判断什么可以完全交出去，什么必须留给你自己拍板

用智能体时有个出人意料的陷阱：把本该由人做的部分也过度分派出去——产品意图、API 设计取舍、架构边界、长期维护决策。

OpenAI 的「AI 原生工程团队」指南把它表述为覆盖软件开发生命周期的三段式划分：分派（delegate）、评审（review）、负责（own）。即便在他们那份乐观的设想里，工程师依然掌握最终决策与签字权，在模糊问题上尤其如此。

这套划分可以干净地映射到编排上。有些工作可以完全分派：规格说明清晰的机械式实现、样板化重构、有强评审兜底的测试生成、文档更新、低风险维护杂活。有些工作可以分派，但你要设检查点、留在回路里：任何触碰共享接口的工作、任何可能产生合并冲突的工作、任何带棘手产品边界情况的工作、任何涉及数据迁移的工作。还有些工作你干脆不分派，或者只让它分派出去探索备选方案：系统架构与新抽象、需要品味的横切重构、产品决策以及「这个该不该做？」的判断、涉及安全关键或隐私敏感的设计决策。

这和团队里派活用的是同一块肌肉：你不断在决定谁负责什么、给多大自主权是安全的、以及在工作固化之前要在哪里设一道检查点。

验证闭环：把问题拦在早期

带人的时候你会学到，最浪费时间的方式就是太晚才去评审低质量的工作。你要的是早期反馈闭环和质量关卡。智能体也一样——只不过它能以高速批量产出低质量工作。

验证闭环是破局点，最优秀的工具厂商正把它写进自己的指南里。Anthropic 的最佳实践明确建议同时运行多个 Claude 实例：一个写代码，另一个通过评审和测试来验证，把它当成一次「职责分离的双人协作」。OpenAI 对 Codex 的定位在工具使用上同样明确：跑命令、跑测试、迭代到通过状态，然后再提 PR。

验证闭环落地长这样：要求智能体跑测试套件（或限定范围的子集），并把输出附在最终回复里；要求改动范围内的 lint 与类型检查必须通过；要求行为变更必须新增或修改对应测试；要求最后交出一份结构化的「PR 材料包」——改了什么、为什么选这个方案、动了哪些文件、测试计划与结果、风险或后续事项。

如果想再进一步，可以用双智能体模式：智能体 A 负责实现，智能体 B 负责评审正确性、风格、边界情况与漏掉的测试，然后再由智能体 A（或新开一个智能体 C）落实评审意见并重新跑一遍验证。这不是理论推演——Anthropic 确实把它作为工作流升级方案写进了推荐里。

管理者的直觉在这里同样重要：你不只是在检查代码能不能编译，还在检查它是否符合约定、是否可维护、是否契合最初意图。

异步进展同步：把智能体当作要向你汇报的下属

如果你同时跑十个并行会话，就不可能挨个翻记录去搞清楚发生了什么。你需要轻量、可复用的进展同步机制。这就是把异步管理的打法套用到智能体上。

定一个同步节奏：「如果 15 分钟内没有实质进展，就停下来报告阻塞点。」并要求按固定格式汇报状态：改了什么？下一步做什么？有哪些风险或阻塞？需要我提供什么？

这看着是小事，但它正是让并行工作不脱轨、又不必全程盯着的办法。要找个具体类比的话，管理智能体很像管理一支跨时区的分布式团队：把清晰度前置，依赖书面更新，把实时注意力留给决策和解除阻塞。

难点是真实存在的（而且都是管理问题）

合并冲突会迅速成倍增长

多个并行智能体改动相邻代码，就像让五个工程师不经协调地改同一个文件。这不是工具失灵，而是边界失守。解法跟带人类团队时一模一样：刻意划清任务边界、隔离工作、定义接口。

实操上，这通常意味着让智能体在隔离的工作目录或分支里跑。Git 工作树（git worktree）是个很干净的模式——同一个仓库可以同时检出多个分支，各自放在独立目录里。Claude Code 的文档明确推荐在并行会话中使用 git worktree，避免实例之间互相干扰；Anthropic 的最佳实践还给出了「worktree + 每个 worktree 一个终端标签页」的分步操作范式。即使用的是云端智能体，原则也相同：分支分开、PR 要小、模块归属清晰。

我最常用的几条边界规则，都是从团队协作里借来的：一个智能体只负责一个 PR，不允许多个智能体拼出一个巨型 PR；如果两个智能体可能碰同一批文件，就重新设计任务拆分；共享接口由人主导、在第一个 PR 里先落地，之后智能体再在这个接缝之上继续构建。

品味与「这个该不该做？」成了真正的瓶颈

当构建变得廉价，你会开始什么都想做。这看起来很高效，直到你的产品变成一个塞满功能的杂物抽屉。

这场转变里有个没被充分讨论的点：AI 并没有消除判断力的必要性，反而抬高了判断力的价值。「该不该做？」开始比「能不能做？」更重要。

这其实是披着外衣的管理能力：排优先级、说不、定义什么叫成功、做小实验、快速掐掉坏点子。

想把它落到实处，可以借两个管理学概念。第一，在制品（WIP）上限：限制同时活跃的智能体任务流数量，免得被评审淹没（正是 Willison 指出的那个瓶颈）。第二，叫停标准：在动手之前就先定义好，出现什么情况就停止推进某个功能。

我享受其中的部分（以及为什么这份投入值得）

「随时随地派活」的效应是真实存在的。当后台智能体能直接对仓库干活、带回来可评审的变更，你就从「先记个 issue 以后再说」变成了「现在就动手把这个想法做出来」。

我目前的做法是：跑 4～5 个后台智能体处理中低复杂度的工作，同时自己在本地另外 3～5 个会话里保持人在回路，处理架构和产品上需要拿捏的工作。能用手机派活，改变了我的创作循环：想法 → 实现草稿 → 评审 → 迭代。

当你有质量标准和一套流程时，这种体验极其令人满足，因为创作循环被缩短了。但只有当你把编排当管理、而不是当魔法时，它才会一直令人满足。你必须对自己同时处理多任务、来回切换的带宽有现实估计。不是每个人都需要同时开 10～15 个智能体。Boris 的工作流更适合作为一个展示「可能性上限」的极端案例，而不是一条硬性要求。

一套简单的编排操作系统

如果你只想练一个可重复的闭环，就用这个：

像管理者一样规划——写清任务简报，包含目标结果、约束条件和验收标准。像编排者一样派发——把任务分配给并行智能体，并给出明确边界。异步监控——轻量进展同步、快速解除阻塞、避免过程中反复折腾。激进验证——测试、lint、结构化 PR 材料包，必要时加第二个智能体做评审。谨慎集成——按深思熟虑的顺序合并，留意越界改动。最后复盘——更新你的 AGENTS.md 和检查清单，让下一轮起步更聪明。

对我们大多数人来说，甜区更接近这样：少量后台智能体处理中低复杂度的工作，而你在架构和产品细节上保持人在回路，同时对自己能承受多少任务切换有现实估计。

这就是编排。而想把它做好，最快的路径是去学那些让一个人能有效带领工程师的能力：清晰表达、任务分派、反馈闭环、异步沟通。
